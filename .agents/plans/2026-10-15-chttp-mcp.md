# @chttp/mcp — Model Context Protocol server, 2026-10-15

## What this is

A Model Context Protocol (MCP) server library for chttp apps. Shipped
as a TypeScript package that compiles to a single static ELF with
`scriptc build`. Users `import { Server, tool, resource, prompt } from
"@chttp/mcp"` and get a JSON-RPC 2.0 MCP server that runs alongside
their chttp routes — same `node:http` server, same `using` ergonomics,
the same Standard-Schema seam for `inputSchema`/`outputSchema`.

**Standard-Schema seam, like the rest of the family.** Validation
runs through Standard Schema v1: the user hands any conforming
validator (`Schema extends StandardSchemaV1`) to `tool(name, schema,
handler)` and checks execute via `schema["~standard"].validate`.
Emission is a second seam: the MCP protocol requires draft 2020-12
JSON Schema for `inputSchema`/`outputSchema`, and Standard Schema v1
standardizes validation only, so the package takes a pluggable
`JsonSchemaEmitter` per tool or per server. Adapters for `@chttp/val`
and valibot are documented in examples, not shipped. No `withSchema`
chain, no codegen, no DSL.

**Same transport-agnostic core as `@chttp/router`.** The MCP protocol
is JSON-RPC 2.0; the wire format is the same regardless of transport.
We model the transport as a `Transport` interface (one method:
`handleRequest(req): Promise<Response>`) with a production
`StreamableHttpTransport` implementation that wires into `@chttp/router`
as a route. A documented example shows the stdio wiring (reading
JSON-RPC requests from `process.stdin` and writing responses to
`process.stdout`), so Claude Desktop and similar stdio-only clients
can talk to a chttp-built MCP server via a thin parent shim.

## Why this package

- **Category-creating.** No npm package today ships "TS handler →
  native ELF → MCP server over HTTP". The official
  `@modelcontextprotocol/sdk` and its 4-5 major descendants
  (fastmcp, mcp-framework, mcp-use, xmcp) all target Node + npm.
  They do not compile to a static binary. This is the first time a
  JS/TS developer can write `tool("add", schema, handler)` and have
  the entire stack compile to a single-file ELF that serves MCP over
  HTTP.
- **Convergent with chttp.** The same `node:http` server, the same
  routing layer, the same validator seam. The MCP server is just a
  chttp route that handles JSON-RPC 2.0 instead of REST. Users
  already using `@chttp/router` add MCP with one extra route.
- **DX precedent.** Cleanest example of the "transport-agnostic core,
  one production transport" pattern. If this package is right,
  every future chttp-internal protocol (LSP? ACP? custom JSON-RPC?)
  follows the same shape: a `Transport` interface + a chttp route
  adapter.
- **DX target user is JS/TS, not protocol engineers.** The whole
  point of chttp is to give web developers a path to native
  binaries. Asking them to hand-roll a JSON-RPC dispatcher, a SSE
  parser, and the MCP `tools/list` response shape would invert the
  project's reason for existing.

## Non-goals

- An MCP **client**. This package is server-only. A separate
  `@chttp/mcp-client` may be built on top later; in v1 the surface
  is "I want to expose tools/resources/prompts to an LLM", not
  "I want to call an MCP server from a chttp app".
- The full Streamable HTTP spec (session IDs, resumability via
  `Last-Event-ID`, event IDs). v1 ships **partial spec, honest
  about it** — JSON-RPC 2.0 over HTTP POST plus SSE progress
  notifications. No session management, no resumability. Documented
  in `docs/streamable-http-coverage.md`.
- A full stdio transport implementation. The `Transport` interface
  supports stdio; an `examples/integrations/mcp-stdio/` shows the
  wiring (~30-50 LoC of `process.stdin`/`process.stdout` plumbing).
  A shipped `StdioTransport` is a v2 ticket.
- The legacy HTTP+SSE transport (pre-2025-03-26). v1 is Streamable
  HTTP only. The MCP spec deprecates the old transport.
- MCP roots, sampling, elicitation. v1 is tools, resources, and
  prompts. Roots (client → server) and sampling (server → client)
  are v2 if asked; both are bidirectional and complex.
- Vendor `@modelcontextprotocol/sdk` or any of its descendants.
  All have subset-banned code (decorator-driven servers in
  mcp-framework; `Map`/`Set`/`Reflect` in mcp-use; class-field
  initializers everywhere). The wire format is JSON-RPC 2.0 — we
  parse it ourselves, ~200-300 LoC.

## Public surface

```ts
import type { StandardSchemaV1 } from "@standard-schema/spec";
import {
  Server, tool, resource, prompt,
  StreamableHttpTransport,
} from "@chttp/mcp";

// ---------- schema seam (type-only import; zero runtime deps)
export type InferOutput<S extends StandardSchemaV1> =
  StandardSchemaV1.InferOutput<S>;
export interface JsonSchemaObject { [k: string]: unknown }
// Emission seam: the MCP protocol requires draft 2020-12 JSON
// Schema and Standard Schema v1 standardizes validation only, so
// emission is injected per tool (`emit`) or per server.
export type JsonSchemaEmitter =
  (schema: StandardSchemaV1) => JsonSchemaObject;

// ---------- core types
export type RequestId = number | string;
export interface JsonRpcRequest {
  jsonrpc: "2.0";
  id?: RequestId;
  method: string;
  params?: { [k: string]: unknown };
}
export interface JsonRpcResponse {
  jsonrpc: "2.0";
  id: RequestId;
  result?: unknown;
  error?: { code: number; message: string; data?: unknown };
}
export type ContentBlock =
  | { type: "text"; text: string; annotations?: Annotations }
  | { type: "image"; data: string; mimeType: string; annotations?: Annotations }
  | { type: "audio"; data: string; mimeType: string; annotations?: Annotations }
  | { type: "resource_link"; uri: string; name: string; mimeType?: string; description?: string }
  | { type: "resource"; resource: { uri: string; mimeType: string; text?: string; blob?: string } };
export interface Annotations {
  audience?: ("user" | "assistant")[];
  priority?: number;
}
export interface CallToolResult {
  content: ContentBlock[];
  structuredContent?: { [k: string]: unknown };
  isError?: boolean;
}

// ---------- server
export interface ServerOpts {
  name: string;
  version: string;
  instructions?: string;        // returned in initialize response
  // Server-level emission seam; a per-tool `emit` overrides it.
  emitJsonSchema?: JsonSchemaEmitter;
  capabilities?: {
    tools?: { listChanged?: boolean };
    resources?: { subscribe?: boolean; listChanged?: boolean };
    prompts?: { listChanged?: boolean };
    logging?: {};
  };
}

export class Server {
  constructor(opts: ServerOpts);

  // The three registration APIs. Each is a thin wrapper that records
  // the registration; the dispatch happens in handleRequest. `emit`
  // (or the server-level `emitJsonSchema`) produces the draft
  // 2020-12 JSON Schema the MCP protocol requires; registration
  // without either throws `E_NO_JSON_SCHEMA_EMITTER` (never `{}`).
  tool<
    Schema extends StandardSchemaV1,
    Out extends StandardSchemaV1 | null = null,
  >(
    name: string,
    schema: Schema,
    handler: (input: InferOutput<Schema>, ctx: ToolContext) =>
      ToolReturn<Out>,
    opts?: {
      description?: string;
      outputSchema?: Out;
      emit?: JsonSchemaEmitter;
    },
  ): this;

  resource(
    uri: string,
    handler: (uri: string, ctx: ResourceContext) =>
      Promise<{ contents: ResourceContents[] }>,
    opts?: { name?: string; description?: string; mimeType?: string },
  ): this;

  prompt(
    name: string,
    handler: (args: { [k: string]: string }, ctx: PromptContext) =>
      Promise<{ messages: PromptMessage[] }>,
    opts?: {
      description?: string;
      args?: Array<{ name: string; description?: string; required?: boolean }>;
    },
  ): this;

  // The single dispatch entry point. Transport-agnostic.
  // Returns the response envelope (or null for notifications).
  handleRequest(req: JsonRpcRequest): Promise<JsonRpcResponse | null>;
}

// ---------- tool context
export interface ToolContext {
  // Server-side: progress notifications (SSE). v1 partial: send a
  // progress notification; the transport decides whether to actually
  // push it to the client.
  progress(progress: number, total?: number): Promise<void>;
  // Server-side: log messages (per MCP spec).
  log(level: "debug" | "info" | "notice" | "warning" | "error" | "critical" | "alert" | "emergency", data: unknown): Promise<void>;
}

export type ToolReturn<Out> =
  | string
  | ContentBlock
  | ContentBlock[]
  | CallToolResult
  | { [k: string]: unknown }  // wrapped as { content: [{type:'text', text: JSON.stringify(v)}], structuredContent: v }
  | null;

export interface ResourceContext {
  log(level: "debug" | "info" | "notice" | "warning" | "error", data: unknown): Promise<void>;
}

export type ResourceContents =
  | { uri: string; mimeType: string; text: string }
  | { uri: string; mimeType: string; blob: string };  // base64

export interface PromptContext {
  log(level: "debug" | "info" | "notice" | "warning" | "error", data: unknown): Promise<void>;
}

export type PromptMessage =
  | { role: "user" | "assistant"; content: ContentBlock };

// ---------- transport
export interface Transport {
  // Handle a single JSON-RPC request. Returns the response envelope,
  // or null for notifications (no `id` field on the request).
  handleRequest(req: JsonRpcRequest): Promise<JsonRpcResponse | null>;
  // SSE progress sink: called when a tool wants to emit progress.
  // The transport decides whether to actually push (HTTP+SSE), buffer
  // (HTTP only), or no-op (stdio in v1 — no async feedback channel).
  pushProgress?(sessionId: string | null, notification: JsonRpcRequest): Promise<void>;
  // Optional: shut down the transport (HTTP server close, stdio flush).
  close?(): Promise<void>;
}

// Streamable HTTP: JSON-RPC 2.0 over HTTP POST. SSE for progress.
export class StreamableHttpTransport implements Transport, AsyncDisposable {
  // chttp route handler. Wires into `@chttp/router` like any other route.
  // Returns a Response that handles JSON-RPC POST + SSE GET (for progress).
  static route(server: Server): (req: Request) => Promise<Response>;
  // Or, as a class with explicit lifecycle:
  constructor(server: Server, opts: StreamableHttpOpts);
  handleRequest(req: JsonRpcRequest): Promise<JsonRpcResponse | null>;
  pushProgress(sessionId: string | null, n: JsonRpcRequest): Promise<void>;
  close(): Promise<void>;
  [Symbol.asyncDispose](): Promise<void>;
}

export interface StreamableHttpOpts {
  // SSE endpoint base path. Default "/mcp".
  endpoint?: string;
  // Whether to accept SSE GET (for progress-only clients). Default true.
  // When false, the transport only supports POST + inline progress.
  allowSseGet?: boolean;
  // Session ID generator. Default: crypto.randomUUID().
  sessionId?: () => string;
  // Maximum request body size. Default 1MB.
  maxBodyBytes?: number;
}
```

### Why this shape

1. **Dual seam: validation standardized, emission injected.** The
   user passes any `StandardSchemaV1` to `tool(name, schema,
   handler)`; `tools/call` validates via `~standard.validate` and
   `InferOutput<Schema>` types the handler input. Emission is the
   one piece Standard Schema v1 does not cover (it standardizes
   validation only), while the MCP protocol requires draft 2020-12
   JSON Schema for `inputSchema`/`outputSchema`. So the emitter is
   an explicit `JsonSchemaEmitter` argument (per-tool `emit`, else
   the server-level `emitJsonSchema`); registering without one
   throws `E_NO_JSON_SCHEMA_EMITTER` naming both documented
   adapters, because an honest error beats silently emitting `{}`.
   Adapters live in docs/examples: one wrapping `@chttp/val`'s
   `toJsonSchema()` (`packages/val/src/json-schema.ts:414-422`,
   the reference adapter, not the package's engine), one for
   valibot's `toJSONSchema` (verify against the installed version
   during implementation). The package ships zero emitters and
   zero validator deps.

2. **Handler return auto-wrap, fastmcp/mcp-framework style.** The
   user can return `string`, `ContentBlock`, `ContentBlock[]`,
   `CallToolResult`, a plain object (auto-wrapped with
   `structuredContent` + a text block carrying the JSON), or `null`
   (no content). The dispatcher's auto-wrap ladder (mirroring
   fastmcp at `FastMCP.ts:2992-3048`):
   - `string` → `{ content: [{ type: 'text', text }] }`
   - `ContentBlock` → `{ content: [block] }`
   - `ContentBlock[]` → `{ content: arr }`
   - `{ content: [...] }` (or with `isError` / `structuredContent`) →
     pass through unchanged
   - plain object → `{ content: [{ type: 'text', text: JSON.stringify(v) }],
     structuredContent: v }` (the dual-content pattern from mcp-use
     at `tools.ts:234-238`)
   - `null` → `{ content: [] }`
   - thrown error → `{ content: [{ type: 'text', text: msg }],
     isError: true }` (official SDK's `createToolError` at
     `packages/server/src/server/mcp.ts:333-343`)

   This is the dominant pattern in the ecosystem (3 of 5 major SDKs
   do it). Subset-clean because every branch maps to a concrete
   `CallToolResult` shape; the wrapper just dispatches on the JS
   shape and constructs the envelope.

3. **Transport-agnostic core, one production transport.** The
   `Server` class only knows JSON-RPC 2.0. The
   `StreamableHttpTransport` is one implementation; an
   `examples/integrations/mcp-stdio/` shows the stdio wiring using
   the same `Transport` interface. This matches the user's
   directive: stdio is a trait/interface in v1, not a full
   implementation.

4. **SSE progress is partial spec, honest about it.** The MCP
   Streamable HTTP spec supports session IDs, resumability via
   `Last-Event-ID`, event IDs, and bidirectional POST/SSE GET. v1
   ships:
   - JSON-RPC 2.0 over HTTP POST (full)
   - SSE for progress notifications (full; the tool calls
     `ctx.progress(n, total)`, the transport pushes a
     `notifications/progress` SSE event)
   - Optional SSE GET for progress-only clients (a `?stream=progress`
     query param; no session ID required)
   - **No session IDs. No resumability. No event IDs.** v2 tickets
     if asked. Documented in `docs/streamable-http-coverage.md` with
     a v1→v2 migration path.

5. **Routes as a function, not a class.** The common case is
   `app.post("/mcp", StreamableHttpTransport.route(server))`. The
   class form exists for users who need explicit lifecycle control
   (e.g. SSE connections that outlive a single request). Both forms
   are subset-clean; the function form is the default.

6. **No `@modelcontextprotocol/sdk` dependency.** The official SDK
   is 13.5K stars, the most-popular, and the de-facto reference.
   But it has subset-banned code (decorator-driven registration in
   mcp-framework descendants, `Map`/`Set` everywhere in mcp-use,
   class-field initializers in tool base classes). The wire
   protocol is JSON-RPC 2.0 — we parse it ourselves, ~200-300 LoC.
   The reference for the protocol is the spec at
   `https://modelcontextprotocol.io/specification/2025-06-18/`.

## JSON-RPC 2.0 dispatch

`Server.handleRequest(req)` is a single switch on `req.method`:

| Method | Behavior |
| --- | --- |
| `initialize` | Return server info + capabilities. First-call semantics. |
| `notifications/initialized` | No-op (notification, no response). |
| `ping` | Return `{}`. |
| `tools/list` | Return registered tools with their emitter-produced `inputSchema` + optional `outputSchema` (same emitter). |
| `tools/call` | Validate `args` via `schema["~standard"].validate`. Call the handler. Auto-wrap the return value into `CallToolResult`. Catch throws → `isError: true` envelope. Emit progress notifications via `ctx.progress`. |
| `resources/list` | Return registered resources. |
| `resources/read` | Call the resource handler, return the contents. |
| `resources/templates/list` | Return empty for v1 (no template support yet). |
| `prompts/list` | Return registered prompts. |
| `prompts/get` | Call the prompt handler, return the messages. |
| `notifications/cancelled` | No-op (best-effort cancellation; v1 has no in-flight query tracking). |
| `notifications/progress` | Server-emitted; the transport handles pushing. The dispatcher is on the receive side too, for completeness. |
| `logging/setLevel` | Set the server's log level; return `{}`. |
| `completion/complete` | v1 returns empty (no completion providers yet). v2 ticket. |
| everything else | JSON-RPC error `-32601` "Method not found". |

The dispatcher is a single function, ~200-300 LoC, subset-clean (no
async generators, no Map/Set, no class-field initializers, indexed
for loops only).

## Streamable HTTP transport

Wires into `@chttp/router` as a single route:

```ts
import { Router } from "@chttp/router";
import { Server, tool, StreamableHttpTransport } from "@chttp/mcp";
import { object, number, toJsonSchema } from "@chttp/val";
import type { StandardSchemaV1 } from "@standard-schema/spec";
// Any Standard Schema v1 validator plugs in; swapping in valibot
// is a one-line import change (import * as v from "valibot").

// Emitter adapters live in docs/examples, never in the package:
const emitVal = (s: StandardSchemaV1) => toJsonSchema(s);
// valibot adapter: const emitValibot = (s) => v.toJSONSchema(s);

const server = new Server({
  name: "chttp-example",
  version: "0.1.0",
  emitJsonSchema: emitVal,     // a per-tool `emit` overrides this
  capabilities: { tools: {} },
});

server.tool(
  "add",
  object({ a: number(), b: number() }),
  async ({ a, b }, ctx) => `${a + b}`,
  { description: "Add two numbers" },
);

const app = new Router();
app.post("/mcp", StreamableHttpTransport.route(server));
app.get("/mcp", StreamableHttpTransport.route(server));   // for SSE GET (progress)
await using server_ = await app.listen({ port: 3000 });
```

POST `/mcp`: receives a JSON-RPC 2.0 request, dispatches, returns the
JSON-RPC 2.0 response. SSE for progress: when a tool calls
`ctx.progress(n, total)`, the transport sends an SSE event with the
`notifications/progress` envelope.

GET `/mcp`: SSE GET for progress-only clients. Optional; the
`allowSseGet: false` opt-out disables it. The transport generates a
session ID, returns it in the `Mcp-Session-Id` response header, and
keeps the connection open for progress events from any in-flight
tool call. v1 sessions are ephemeral (one connection = one session);
no resumability, no event IDs, no `Last-Event-ID` support.

The `Mcp-Session-Id` response header is set; v1 ignores it on the
client side (the client doesn't need to send it back because the
transport doesn't have a session store). Documented as "set but
unused in v1; required for spec compliance".

## Stdio transport (interface + example, not a shipped impl)

The `Transport` interface is the seam. The stdio wiring is ~30-50
LoC of `process.stdin`/`process.stdout` plumbing:

```ts
// examples/integrations/mcp-stdio/main.ts
import { Server, tool, StreamableHttpTransport } from "@chttp/mcp";

const server = new Server({ name: "stdio-mcp", version: "0.1.0", capabilities: { tools: {} } });
server.tool("echo", /* any schema */, async (args) => args, { emit });

process.stdin.setEncoding("utf-8");
let buf = "";
process.stdin.on("data", (chunk: string) => {
  buf += chunk;
  let nl: number;
  while ((nl = buf.indexOf("\n")) !== -1) {
    const line = buf.slice(0, nl).trim();
    buf = buf.slice(nl + 1);
    if (line.length === 0) continue;
    const req = JSON.parse(line) as JsonRpcRequest;
    server.handleRequest(req).then((res) => {
      if (res !== null) process.stdout.write(JSON.stringify(res) + "\n");
    });
  }
});
```

This is the v1 stdio story: an example that users can copy and
adapt. A shipped `StdioTransport` class is a v2 ticket; the
interface is there so the example is a thin adapter, not a
workaround.

The `pushProgress?` optional method on `Transport` is the seam for
stdio to no-op progress notifications (stdio is request/response,
not async-event).

## Dependencies

- **Zero runtime dependencies.** `@standard-schema/spec` is a
  type-only import (the validation seam); JSON-Schema emission is
  injected per tool or per server, so nothing validator-shaped
  ships in the tarball. `@chttp/val` and valibot appear only as
  dev-deps for seam-proof tests and as documented adapter
  providers.
- `@chttp/router` is a **peer-dep**. `StreamableHttpTransport` wires
  into a chttp route via `app.post("/mcp", handler)`. The peer-dep
  is `>=0.1.0`; the route handler is a `(req: Request) =>
  Promise<Response>` function, which the router already accepts.
- `@modelcontextprotocol/sdk` is **not** a dependency. Subset-banned.
  Reference only — we read the spec and the wire shapes, not the
  code.
- Any descendant SDK (fastmcp, mcp-framework, mcp-use, xmcp) is
  **not** a dependency. Same reasoning; subset-banned code.
- `node:events` is **not** a peer-dep. We don't ship an event
  emitter. Subset-hostile anyway.
- `zod`, `valibot`, `arktype` are **not** peer-deps. Validators are
  runtime-agnostic through the seam: anything `StandardSchemaV1`
  plugs in. valibot is a first-class documented option (verified
  compiling under scriptc 0.3.3); zod and arktype work at
  Node-time but do not compile to native. There is no "second
  validator" ticket; the registration API already takes any
  conforming validator.

## Testing strategy

1. **Dispatcher unit tests** (`test/dispatch.test.ts`) — every
   method on `Server.handleRequest`, every error path. Mock the
   handler returns; assert the envelope shape.
2. **Auto-wrap ladder tests** (`test/wrap.test.ts`) — every branch
   of the return-value wrapper. String → text block; block → array;
   array → array; object → dual content; null → empty content;
   throw → `isError: true`. ~20 cases.
3. **JSON-RPC 2.0 parsing tests** (`test/jsonrpc.test.ts`) — valid
   requests, malformed requests, missing `jsonrpc` field, bad `id`
   type, batch requests (out of scope; we don't support batches in
   v1), notification vs request.
4. **SSE format tests** (`test/sse.test.ts`) — event encoding,
   `data:`, `event:`, `id:`, multi-line `data`, retry intervals.
   No `for await` in the encoder (we write each event synchronously
   to the response stream).
5. **HTTP transport tests** (`test/http.test.ts`) — POST flow,
   SSE GET flow, error responses, content-type negotiation. Uses
   a `node:http` mock server (not `koffi`; FFI-free package).
6. **MCP spec compliance** (`test/spec.test.ts`) — golden test
   vectors from the MCP spec. The spec publishes JSON examples for
   every method; we read those, run them through the dispatcher,
   assert the response matches the spec's expected shape.
7. **Subset gate** (`test/coverage.test.mjs`) — `scriptc coverage`
   100% on the wrapper source.
8. **End-to-end smoke** (`test/elf.test.sh`) — `scriptc build` a
   small program that runs an MCP server, sends a `tools/list`
   request, asserts the response.

Test baselining per global rule 9c: full suite →
`/tmp/chttp-mcp-baseline-<ts>.log` before iterating, diff before
done.

## Scope discipline

- **Do not** add MCP roots, sampling, or elicitation in v1. All three
  are bidirectional and complex; v2 tickets if asked.
- **Do not** add session ID management, resumability, or event IDs
  to Streamable HTTP in v1. The `Mcp-Session-Id` header is set but
  ignored. Documented as partial spec coverage.
- **Do not** add a full `StdioTransport` class. The
  `examples/integrations/mcp-stdio/` shows the wiring; a shipped
  class is v2.
- **Do not** add an MCP **client**. v1 is server-only. A separate
  `@chttp/mcp-client` is a v2 ticket.
- **Do not** vendor any MCP SDK. The wire is JSON-RPC 2.0; we parse
  it ourselves.
- **Do not** add a query DSL, schema DSL, or codegen. Standard
  Schema v1 in, JSON Schema out via the injected emitter. The
  dispatcher touches `~standard.validate` and emitter results and
  nothing else.
- **Do not** add `subscribe` resource support. Resources in v1 are
  read-on-demand; `resources/subscribe` and the `notifications/
  resources/updated` event are v2.
- **Do not** widen the public surface beyond the ~15 methods
  above. New method = new test + new docs + new subset-coverage
  gate.

## Risk register

- **Subset regressions in the wrapper.** Mitigation: `scriptc
  coverage` in CI, 100% gate. Same gate as `@chttp/val`,
  `@chttp/router`, `@cutils/*`.
- **MCP spec drift.** The spec is at revision 2025-06-18 today;
  the project tracks it. A new spec revision is a v2 release of
  this package. We pin the spec version in `package.json` and in
  `docs/streamable-http-coverage.md`.
- **JSON-RPC 2.0 edge cases (batches, malformed envelopes).**
  Mitigation: comprehensive `test/jsonrpc.test.ts`; we don't
  support batches in v1 (documented); malformed envelopes return
  `-32700` (Parse error) per spec.
- **SSE partial-spec coverage surprises users.** Mitigation:
  `docs/streamable-http-coverage.md` lists exactly what's in v1 and
  what isn't. The `Mcp-Session-Id` header is set but unused; this
  is documented as spec-compliance without functionality.
- **Standard Schema spec drift.** Mitigation: the seam is the
  type-only `StandardSchemaV1` import plus `~standard.validate`, a
  frozen v1 contract; a spec revision is a major bump of this
  package, not a silent change.
- **Emitter adapters drift from validator versions** (val
  `toJsonSchema`, valibot `toJSONSchema`). Mitigation: adapters
  live in docs/examples, so a validator-version mismatch is fixed
  in userland; the package's only contract is the emitter
  signature.
- **`@chttp/router` request shape drift.** Mitigation: pin the
  peer-dep; the route handler is a `(req: Request) => Promise<
  Response>` function (Web Fetch API standard, not chttp-specific).
  The peer-dep is required because `StreamableHttpTransport.route`
  imports `Request`/`Response` from `@chttp/router`'s exports.
- **Auto-wrap surprises users who want the raw envelope.**
  Mitigation: handlers can return a `CallToolResult` directly to
  pass through unchanged. Documented in `docs/auto-wrap.md`.
- **SSE connection limits.** Default `node:http` is 5 connections
  per origin. v1 doesn't add connection pooling; users who need
  it can run multiple chttp processes behind a load balancer. v2
  ticket if asked.
- **The `Transport` interface is a contract.** v1 only ships
  `StreamableHttpTransport`. Adding a `StdioTransport` impl is a
  v2 ticket that requires the interface to stay stable. We
  commit to the interface in `src/transport/stdio.ts`.

## Cross-cutting (ripples to other packages)

- **`@chttp/router`** — `@chttp/mcp` mounts as a route; the route
  handler is a standard `(req: Request) => Promise<Response>`
  function. The router's `app.post()` / `app.get()` accept this
  shape. No router changes needed.
- **`@chttp/val`** — `@chttp/mcp` consumes only
  `schema["~standard"].validate` in-package; JSON-Schema emission
  goes through the adapter, so val is an adapter provider, not a
  dep. `src/validate.ts` is the seam module (same shape as the DB
  family's `validate.ts`). No val changes needed.
- **`@cutils/sqlite` / `@cutils/postgres` / `@cutils/mongo`** —
  the `examples/todo-mcp/` example wires an MCP server to a
  chttp + sqlite + val app, demonstrating that one
  Standard-Schema validator serves HTTP request bodies, MCP tool
  args, and DB rows. No DB changes needed.
- **All `@chttp/*` and `@cutils/*` packages** — `@chttp/mcp` is the
  third "transport-agnostic core, one production transport"
  pattern in chttp (after `@chttp/router`'s route+server split and
  the DB family's transport+driver split). The pattern is
  convergent: a `Core` class + a thin `Transport`/`Driver` adapter.
